# 보안

이 사이트는 서버 코드 없이 브라우저가 Supabase에 직접 접속합니다. 그래서 **브라우저에 있는 것은 전부 공개된 것**으로 보고, 실제 방어는 데이터베이스(RLS·함수·권한)에 둡니다.

## 절대 규칙

- **`service_role`/`secret` 키는 이 저장소, `VITE_*` 변수, GitHub 변수·Secrets, 브라우저 어디에도 넣지 않습니다.** 이 키는 RLS를 무시하므로 노출되면 모든 회원·주문 정보가 열립니다. 이 프로젝트는 그 키가 필요한 기능이 없습니다(Edge Function 없음). DB 비밀번호도 마찬가지이고, 예외는 백업 워크플로의 GitHub **Secret** `SUPABASE_DB_URL` 하나입니다([DEPLOY 7절](DEPLOY.md#7-백업멈춤-방지)). 저장소에 쓰기 권한이 있는 사람은 워크플로를 고쳐 Secrets를 꺼낼 수 있으니 협업자는 최소로 둡니다.
- 사이트에 들어가는 키는 Project URL과 Publishable(또는 legacy `anon`) 키 둘뿐입니다. 이 키는 공개돼도 되도록 설계되어 있고, 권한은 RLS가 막습니다.
- `.env.local` 등 `.env*` 파일은 커밋하지 않습니다(`.env.example`만 예외).
- 관리자 지정은 SQL로만 합니다([HANDOVER 2.2](HANDOVER.md#22-supabase-클라우드-프로젝트) 11단계). 관리자는 인증 앱(TOTP) 2단계 인증을 마쳐야만 관리자 권한을 받습니다.

## 관리자 계정 보호

- 관리자 계정은 긴 고유 비밀번호 + 비밀번호 관리자 사용, 공용 PC에서 로그인하지 않기, 관리자 수 최소화.
- **2단계 인증(TOTP)**: 적용됨(점검 목록 17번). 관리자는 첫 로그인 때 인증 앱을 등록하고, 이후 로그인마다 6자리 코드를 입력합니다. 데이터베이스가 `aal2` 세션만 관리자로 인정하므로 화면을 우회한 API 요청도 비밀번호만으로는 관리자 데이터를 읽거나 바꿀 수 없습니다. 고객 계정에는 2단계 인증 화면이 없습니다.
- **인증 앱 분실·교체**: 본인 확인 후 SQL Editor에서 등록된 인증 앱을 지우고 모든 기기에서 로그아웃시킵니다. 다음 로그인 때 등록 화면이 다시 나옵니다([HANDOVER 3절](HANDOVER.md#관리자-인증-앱-분실교체)).
  ```sql
  delete from auth.mfa_factors where user_id = (select id from auth.users where email = 'owner@your-domain.com');
  delete from auth.sessions    where user_id = (select id from auth.users where email = 'owner@your-domain.com');
  ```
- Supabase Dashboard 계정 자체(조직 소유자)에도 2단계 인증을 켜세요. 이 계정이 털리면 모든 것이 열립니다.

## 봇 방지 CAPTCHA (운영 전 권장)

가입·로그인·비밀번호 재설정에는 지금 IP별 요청 한도만 있습니다. Cloudflare Turnstile을 켜면 가입 봇, 메일 폭탄, 비밀번호 대입을 막을 수 있습니다. 아직 코드에는 없으며, 켜려면 아래 순서대로 작업합니다. **3을 배포하기 전에 2를 켜면 모든 로그인·가입이 `captcha_failed`로 막힙니다.** 서버에서 꺼져 있을 때 보낸 토큰은 무시되므로 3 → 2 순서가 안전합니다.

1. **키 발급**: [Cloudflare 대시보드](https://dash.cloudflare.com) → Turnstile → 위젯 추가. 호스트 이름에 사이트 도메인을 넣고 Site Key와 Secret Key를 복사합니다. 운영 키에는 `localhost`·`127.0.0.1`을 넣지 말고, 로컬·e2e에서는 Cloudflare 테스트 키(Site Key `1x00000000000000000000AA`, Secret Key `1x0000000000000000000000000000000AA`, 항상 통과)를 씁니다.
2. **Supabase 설정**: 운영은 Dashboard → Authentication → Attack Protection(Bot and Abuse Protection) → **Enable CAPTCHA protection** → Provider `Turnstile`, Secret Key 입력 → Save. 로컬은 `supabase/config.toml`의 `[auth.captcha]` 주석을 풀어 `enabled = true`, `provider = "turnstile"`, `secret = "env(SUPABASE_AUTH_CAPTCHA_SECRET)"`로 두고, 셸에 테스트 Secret Key를 넣은 뒤 `supabase stop && supabase start`.
3. **프론트 코드**: Site Key를 `VITE_TURNSTILE_SITE_KEY`로 추가(`src/config/env.ts` 스키마, `.env.example`, GitHub 변수, `deploy.yml`의 Build `env`). 위젯(`@marsidev/react-turnstile` 또는 `https://challenges.cloudflare.com/turnstile/v0/api.js`)을 로그인·가입·비밀번호 찾기·인증 메일 재발송 화면과 비밀번호를 다시 확인하는 화면(회원정보, 탈퇴)에 넣고, 받은 토큰을 `options: { captchaToken }`으로 넘깁니다. 대상 호출: `signInWithPassword`(`src/features/auth/api.ts`, `src/features/account/api.ts`의 `verifyPassword`), `signUp`, `resend`, `resetPasswordForEmail`. 토큰은 한 번만 쓸 수 있으니 요청이 끝날 때마다 위젯을 초기화합니다. e2e의 `anonClient().auth.signUp`(서버 거부 확인)도 테스트 토큰 `XXXX.DUMMY.TOKEN.XXXX`를 넘기도록 고칩니다.
4. **CSP**: `vite.config.ts`의 `script-src`와 `frame-src`에 `https://challenges.cloudflare.com`을 추가하고 위 점검 목록 7번(콘솔 CSP 위반 0)을 다시 확인합니다.

## 사고 대응

- **anon/publishable 키 노출**: 공개용 키라 노출 자체는 문제가 아니지만 남용이 의심되면 Dashboard → Project Settings → API Keys에서 새 키를 만들고 GitHub 변수 교체 → 재배포 → 옛 키 폐기.
- **secret/service_role 키 노출**: 즉시 키 회전(legacy JWT 키라면 JWT secret 회전, 모든 세션 무효화), Auth·DB 로그에서 이상 접근 확인, 개인정보 유출이 의심되면 개인정보보호법에 따라 정보주체 통지와 신고(1천 명 이상이거나 해킹 등 외부 공격이면 72시간 안에 개인정보보호위원회·KISA 신고)를 검토합니다.
- **DB 비밀번호(`SUPABASE_DB_URL`)·`CLOUDFLARE_API_TOKEN` 노출**: Dashboard → Database → Settings에서 DB 비밀번호 재설정 후 Secret 갱신 / Cloudflare My Profile → API Tokens에서 토큰 Roll 후 Secret 갱신. `BACKUP_PASSPHRASE`가 노출되면 새 문구로 바꾸고 옛 백업 아티팩트를 지웁니다.
- **관리자 계정 탈취 의심**: `delete from public.admins where user_id = …`로 즉시 권한 제거 → Dashboard → Authentication에서 해당 사용자 로그아웃/비밀번호 재설정 → 관리자 → 설정의 변경 기록에서 무엇이 바뀌었는지 확인.
- 사고 뒤에는 위 점검 목록 2·4·5번(RLS·권한)을 다시 확인하세요.
